## 已复现

### B01 [P1] 去选菜再返回导致规划草稿丢失

路径：首页输入需求 -> 登录回跳新建计划 -> 手动设为 2 天 / 2 人 -> 继续选菜 -> 加入两道菜 -> 去安排。

实际：需求框清空，天数回到 3 天、人数回到 1 人。只有已选菜保留。
预期：正常选菜往返应保留全部草稿，不能要求重新填写。
影响：用户容易提交错误的天数/人数，也会丢失关键限制。

### B02 [P2] 自然语言与结构化表单相互矛盾，未提示

首页输入“两天晚饭，两个人，少盐，每餐30分钟内，不用烤箱”。登录回跳后文本保留，但控件仍显示 3 天、1 人。
预期：明确提取已知人数/天数，或提示需确认的冲突，不静默保留不一致默认值。

### B03 [P2] 首页文字规划入口实际要求先选足菜谱

首页填写需求并点开始规划后，还必须选择至少与天数相同数量的菜。
新建页无菜时“生成菜单”仍可点，点击后才提示“规划 3 天至少需要选择 3 道菜”。
性质：产品路径预期不一致，不是接口崩溃；若坚持候选池模式，应在入口清晰表达，未满足条件时引导选菜。

### B04 [P1] 整体调整陷入重复确认，无法执行

在本轮计划输入“这份菜单感觉不太合适” -> 出现“确认调整” -> 点击 -> 显示正在调整 -> 又出现完全相同的确认。连续两次确认均如此，菜单仍是第一版。
预期：确认后执行一次，完成或给出具体失败/澄清；不能回到同一个未确认状态。

### B05 [P1] 待确认操作没有取消出口，后续输入被堵住

在 B04 待确认时输入“先不要重排，只去掉第二天的香菜”，发送按钮始终禁用。页面只有“确认调整”，没有取消/拒绝/改口入口。
预期：用户可取消高影响调整后继续对话，而不是只能接受或离开。

### B06 [P2] 模糊不满意被直接理解成全局重规划

“这份菜单感觉不太合适”没有表达修改范围，系统却直接请求确认重排多天，未先问口味、食材、时间或哪一天。
预期：最小澄清问题；不要把未知意图默认放大成全局动作。

### B07 [P2] 详情页的“返回发现”丢失分类上下文

素食分类 -> 牛肉小火锅详情 -> 页面“返回发现” -> 回到无参数推荐页，原素食筛选丢失。
搜索空结果与清除筛选能正常工作；本问题是页面返回链接，不是浏览器后退按钮。
